# 실시간 전투 설계 v1 — 드래곤 러쉬 (Dragon Rush)

> 상태: **전투 sim과 §9 온라인 롤백 경로 구현됨**. 상성 보정·체감 지연 검증은 진행 중이다.
> **수치는 v1 기본값이며 `packages/combat`의 `DEFAULT_COMBAT_RULES`가 정본**이다. 문서와 코드가 다르면 코드를 따르고 이 문서를 고친다. 값은 플레이테스트로 조정한다(§11 노브).
> 정본 분담: 보드 규칙·수치 → [game-design.md](game-design.md) · 전투 AI(`cobs_v1`/`cact_v1`, combat env) → [combat-ai-spec.md](combat-ai-spec.md) · 연출·효과·히트스톱 표 → [art-direction.md](art-direction.md) · 패키지 구조·프로토콜 → [architecture.md §12](architecture.md) · 일정 → [development-plan.md §5](development-plan.md)
> 단위: **f** = sim 틱(60Hz, 16.7ms), **px** = 논리 픽셀(960×540 캔버스, 1080p에서 2배 렌더), 1타일 = 32px.

## 0. 원칙
1. **보드 규칙은 그대로**다. 바뀌는 것은 결투(PvP)와 용 도전을 **실시간 2D 탑다운 액션**으로 해결한다는 점 하나다. 기존 주사위 해결은 `dice` 모드로 남긴다(학습·빠른 진행·대체 경로).
2. **학습 모델 2개 + 스크립트 1개**: 보드 정책(`obs_v1`/`act_v1`, 변경 없음), 전투 정책(`cobs_v1`/`cact_v1`, 신규, 별도 학습 환경), 용 = 결정적 스크립트 상태기계(학습 모델 아님).
3. **결정성 경계**: `packages/combat`은 순수 정수 TypeScript다. 표현(FX·카메라·오디오)은 sim 이벤트를 구독만 하고 자기 RNG와 시계를 쓴다. sim 안에는 히트스톱·넉백·예고 시간·입력 버퍼만 둔다(학습과 실전이 같아야 함).
4. **보드 직업 패시브는 모두 실시간 형태로 유지**한다(§5). HP는 보드 HP와 1:1이고 전투 후 다시 보드에 기록된다.
5. **시간 목표**: 결투는 보통 20~30초(상한 45초), 용전 상한 75초. 한 판 7~10분 목표(Phase R7)의 일부다.

## 1. sim 상수
| 항목 | 값 |
|---|---|
| 틱 | **60Hz 고정**, 정수 틱 카운터. 클라이언트: 누산기(프레임 시간 0.25초로 클램프, 프레임당 최대 5스텝), `alpha = acc/dt`로 보간 렌더 |
| 단위 | 위치·속도 **Q8** 정수(1px = 256). 1600×1000px 경기장도 2^19 미만이라 거리 제곱이 double에서 정확 |
| 경기장 | **PvP 800×448**(25×14타일), **용 896×448**(28×14). 둘 다 56px HUD 띠 아래 중앙. 여백 ≥ 29px(1.06배 줌 펀치에도 안 잘림). v1은 장애물 없음 |
| 각도 | 256단계 **BAM**(u8). sin/cos는 **하드코딩한 256개 Q14 테이블**(런타임에 `Math.sin`으로 생성 금지). 정수 `atan2` = 옥탄트 축소 + 33개 테이블 |
| sim 금지(ESLint `no-restricted-properties`) | `Math.sin/cos/tan/atan2/exp/log/pow/sqrt/hypot/cbrt`, `**`, `Math.random`, `Date`, 객체 키 순서에 의존하는 반복. 이유: ECMAScript가 이 함수들을 "근사 허용"으로 두어 V8·SpiderMonkey·JavaScriptCore 결과가 다를 수 있음. `+ − × ÷`와 `floor/round/imul/fround`는 정확 |
| 충돌 | 원-원, 근접 호 = 원 + 방향 테이블과의 내적 판정, 거리 제곱만 비교 |
| RNG | 전투마다 별도 스트림(`combatSeed`). 쓰는 곳: 용 기술 선택(v1). 닌자 회피는 RNG가 아니라 카운터(§5) |
| 입력 | 7비트 마스크 `{up, down, left, right, attack, skill, dash}`. 레벨로 읽고, 누름 = 상승 에지. **버퍼 6 라이브 틱**(히트스톱 중 정지) |
| 결정성 검사 | 60틱마다 packed state의 FNV-1a 해시. 골든 리플레이: Vitest(Node) + Playwright(Chromium·Firefox·WebKit). 무작위 입력 1만 판 퍼즈 |
| 리플레이 기록 | `{seed, setup, 틱별 입력 ×2, outcome, hash}`, 원본 약 20~40KB/전투, run-length 압축 후 게임 로그에 저장 |

## 2. 조작
### 2.1 입력 모델 (사람·네트워크·AI 공통)
- 8방향 이동: 4틱에 최고 속도, 3틱에 정지(미끄러지지 않음).
- 바라보는 방향 = 마지막 0이 아닌 이동 방향. 공격 시작·유효 프레임 동안, 활을 당기는 동안 고정(측면 이동 가능).
- 조준 = 바라보는 방향 + **소프트 조준 보정**: 공격 시작 시 대상이 ±25°·사거리 1.5배 안이면 정확한 BAM 각도로 맞춘다. 사람과 AI가 같은 보정을 받는다. v1은 마우스 조준 없음(로컬 2인이 마우스 하나를 못 나눔, AI와 행동 공간 동등성 유지).
- 연타 공격(검사 3연타, 닌자 2연타): 현재 타의 동작 중에 누르면 다음 타가 예약된다(체인 플래그, 회복 끝에 소비). AI의 4틱 결정 주기로도 연타가 된다 [v1 판단].
- 버튼을 계속 누르고 있으면 홀드(궁수 당기기). 네트워크 누락 입력은 마지막 마스크 전체를 반복하므로 새 에지가 생기지 않고 홀드가 유지된다.

### 2.2 키 배치 (`KeyboardEvent.code`로 읽음, 모두 재지정 가능)
| 플레이어 | 이동 | 공격 | 스킬 | 대시 |
|---|---|---|---|---|
| P1 핫시트 (**도착자/도전자**) | WASD | F | G | H |
| P2 풀 키보드 (방어자) | 방향키 | Numpad1 | Numpad2 | Numpad3 |
| P2 노트북·TKL | 방향키 | `,` (Comma) | `.` (Period) | `/` (Slash) |
| 솔로 / 온라인 / vs 용 | WASD 또는 방향키 | J 또는 Z | K 또는 X | L, C 또는 Space |
| 게임패드 (둘 다) | 스틱(데드존 0.35, 8방향 양자화) 또는 D-pad | South | West | East 또는 RB |

- **Shift·Ctrl·Alt·Tab·Meta는 절대 배정하지 않는다**: Shift 5번 = Windows 고정 키 대화상자, Chrome은 Ctrl+W/T/N을 페이지가 막지 못함(P2의 Ctrl + P1의 W = 탭 닫힘), Alt+← = 뒤로 가기.
- Space·방향키·`/`에 `preventDefault`(Firefox는 `/`에서 빠른 찾기). `blur`·`visibilitychange` 때 눌린 키를 모두 해제. `.code`는 한글 IME 조합 중(`key: "Process"`)에도 동작한다.
- **"키보드 테스트" 화면**: 8개 키 동시 입력을 불빛으로 보여 주고, 막히는 키가 있으면 대체 배치를 권한다(멤브레인 키보드 고스팅 대비). 게임패드는 Gamepad API로 두 플레이어 모두 지원.

## 4. 피해 공식
```
dmg = max(1, roundHalfUp( S · P · ATK_eff · K / (K + DEF_eff) )) + flat
S = 8/5 (1.6)    K = 10    P = 기술 위력(기본 1.0, 마무리 1.5~1.8, 스킬 2.0~2.5)
ATK_eff = ATK × 13/10   (광전사 ∧ 2·hp ≤ maxHp)
DEF_eff = DEF/2 (마법사의 공격) · 0 (용 브레스, 보드 규칙과 같음) · 그 외 DEF
flat    = +3   (궁수가 처음 맞힌 공격, 감쇠 후 더함)
```
- 정수 분자·분모로 계산하고 `floor((2·num + den) / (2·den))`로 반올림한다. 분산·치명타 없음.
- 뺄셈 공식(ATK − DEF) 대신 나눗셈: 보드 크기 숫자에서 0 피해·큰 변동이 없고, DEF 1점이 항상 실효 HP +1/K(10%)를 준다. S는 실제 시작 스탯 중앙값에서 동일 스탯 기본타 약 8회로 KO되도록 정했다.
- 용 머리 약점은 P × 3/2.

| 대결 (P 1.0, 다른 표기 제외) | 피해 | 처치 타수 |
|---|---|---|
| 검사 ATK 5 → 궁수 (DEF 6, HP 39) | 5 | 8 |
| 궁수 6 → 검사 (DEF 5, HP 56): 빠른 사격 P 0.7 / 완전 사격 P 1.6 | 4 / 10 | 14 / 6 |
| 마법사 4 → 닌자 (DEF 5→2.5, HP 30): 화살 P 0.9 | 5 | 6 |
| 닌자 4 → 광전사 (DEF 5, HP 49): 단검 P 0.6 | 3 | 17 찌르기 (연타 9회) |
| 광전사 5 → 검사: 도끼 P 1.8 (광폭) | 10 (12) | 6 (5) |
| 용 10 → DEF 5: 발톱 P 1.2 / 브레스 틱 P 0.4 (DEF 무시) | 13 / 6 | 발톱 3~5회 |
| ATK 5 → 용 (DEF 6) | 5 (머리 8) | 기본타 23회 |

## 6. 결투 규칙
| 항목 | 값 |
|---|---|
| 시작 | 가로 중앙선에 480px 간격, 서로 마주 봄. **도착자 = 왼쪽, P1 키**. 준비 1.5초 후 "싸워라!" = 틱 0 |
| 제한 시간 | **45초 (2,700틱)** |
| 불의 고리 | 경기장 중앙의 원. 반지름이 **30.0초 → 40.0초**(1,800 → 2,400틱) 동안 460 → 180px로 선형 축소 후 유지. 460px는 경기장 대각선 절반(≈458px)보다 커서 30초 전에는 밖이 없다 |
| 고리 밖 | 30틱마다 2 HP, DEF 무시, 사망 가능, 닌자 회피 카운터에 포함. 60px/s로 안쪽으로 밀림 |
| 시간 종료 | HP 비율이 높은 쪽 승리, `hpA·maxHpB` vs `hpB·maxHpA`로 정확히 비교. 완전 동률이면 **도착자** 승리(엔진 `capTieWinner: 'a'`와 같음). 서든데스 없음 |
| 기록 | 승자 HP와 불굴 사용 여부를 보드에 기록. 패자는 보드와 같이 탈락(전리품 이전은 엔진이 처리) |
| 방어막 아이템 | 전투 시작 전 보드에서 결투를 취소한다(변경 없음) |
| 초반 보호 | `pvpGraceRounds` 동안은 전투 자체가 없다(변경 없음) |

## 7. 용 보스 (스크립트, 결정적)
### 7.1 몸체
- 스탯은 보드와 같다: HP 115 / ATK 10 / DEF 6, 같은 공식, 브레스는 DEF 무시. HP는 도전마다 리셋.
- 위쪽 중앙에 고정, 스프라이트 약 192×144px. 몸 허트박스 = 반지름 40 원 3개로 근사한 타원. 머리 r 28은 숙였을 때(브레스 후 48f, 돌진 기절 90f) ×1.5 약점. 접촉 피해 없음. 플레이어의 x를 따라 60px/s로 옆으로 이동.
- 플레이어는 아래 중앙, 용에게서 320px 떨어져 시작.

### 7.2 기술 선택
- 거리 구간별 가중치를 둔 시드 선택. 기술 사이 대기: 1페이즈 96~132f, 2페이즈 78~108f.

### 7.4 페이즈
- **1페이즈** HP 100~60%: 기술 1~4, 6.
- **2페이즈** 60~25%: 예고 −12%, 돌풍 → 화염구 연계, 5발 화염구, 휩쓸기 브레스.
- **3페이즈** ≤ 25%: 강하 추가, 회복 −25%. 짧게 유지한다(Cuphead: 마지막 페이즈가 가장 길거나 어렵지 않게).
- 페이즈 전환마다 60f 포효: 용 무적, trauma 0.5, 모든 투사체 제거.

### 7.5 제한 시간
- **50초 (3,000틱)**: 소프트 격노 — 기술 사이 대기 ×0.8. "3번째마다 브레스"는 유지.
- **75초 (4,500틱)**: 도전자 패배(엔진 `capLoser: 'a'`와 같음). 타이머는 항상 크게 보인다.
- 75초로 줄었으므로 승률 목표를 맞추려면 `dragonDamageTakenScale` 기본값을 다시 조정할 수 있다(§7.7).

### 7.6 공정성 규칙
- 모든 위험은 대시 한 번(수직 이동 ≤ 128px)으로 피할 수 있다.
- 모든 공격은 모양·색·고유 소리 세 겹으로 예고한다. 피해 = 빗금 엠버, 밀어내기 = 달빛 파랑. 위험 종류는 화면에 최대 2개.
- 회복 길이는 예고 길이에 비례한다. 피해량은 보이는 위험도와 맞춘다.

### 7.7 튜닝 노브
- `dragonDamageTakenScale` 기본 1.0. 목표: Normal 봇이 시작 스탯으로 이길 확률 < 10%, ATK 9 / DEF 8 / HP 70이면 약 50%.

## 8. 보드와의 연결
### 8.1 엔진 COMBAT phase (병행 구현 중, 이름은 엔진 코드가 정본)
- `RulesConfig.combat.mode: 'dice' | 'external'`. `dice`는 지금처럼 `applyAction` 안에서 주사위로 자동 해결한다. `external`이면 엔진이 `CombatStarted` 이벤트를 내고 `phase = 'COMBAT'`, `pending.actor = a`, `state.combat = CombatRequest { kind: 'duel' | 'dragonFight', a, b }`에서 멈춘다. 이 phase의 보드 합법 행동은 없다(`getLegalActions` = `[]`).
- 셸(서버·`LocalGameClient`·env)이 전투를 실행하고 `applyCombatResult(state, CombatResult)`로 결과를 넣는다: `{ winner: 'a'|'b', hpA, hpB (용전 null), indomitableUsedA?, indomitableUsedB?, timedOut? }`. 엔진이 결과를 검증한 뒤 `CombatEnded`, 탈락·전리품·승리 판정을 이어서 처리한다.
- `resolveCombatWithDice(state)`: 대기 중인 전투를 기존 주사위 규칙으로 정리한다(`dice` 리졸버, 오류 시 대체 경로).
- 실시간 모드의 게임 로그에는 요약 이벤트(`CombatStarted`/`CombatEnded`)만 남고, 교환별 `CombatHit`은 없다. 전투 내용은 전투 리플레이(§1)에 저장한다.
- 전투 시드는 `CombatRequest`에 없으므로 셸이 정해 리플레이에 기록한다(온라인 = 서버 CSPRNG, 로컬 = `crypto.getRandomValues`, env = 에피소드 시드에서 파생).

### 8.2 흐름
1. 보드: 도착·방어막 결정이 끝나면 엔진이 `COMBAT`에서 멈춘다. 서버는 보드 턴 타이머를 멈춘다.
2. 전환 2.8초: 보드 1.15배 줌 → 발톱 와이프 → VS 1.3초 → 준비 1.5초(키 힌트, 온라인은 이 동안 RTT 측정).
3. 전투(결투 ≤ 45초, 용전 ≤ 75초) → KO 또는 시간 종료.
4. 결과 카드 1.2초 → 보드 복귀 600ms → `applyCombatResult` → 모서리 카드 HP 카운트다운.
- **전투 1회 고정 비용 ≈ 5.5초 + 전투 시간**. 평균 결투 20~30초면 전투 하나가 약 25~35초다. 7~10분 목표(Phase R7)의 시간 예산에 넣는다.

### 8.3 실시간 매치업
| 매치업 | 실행 위치 | 비고 |
|---|---|---|
| 사람 vs 사람, 핫시트 | 브라우저 sim | P1/P2 키 배치 또는 게임패드 |

## 9. 온라인 넷코드 (구현됨; 핫시트·오프라인은 로컬 sim)

### 9.1 권위와 모드
- `@dragon-rush/netcode`의 `FightAuthority`가 서버에서 60Hz 전투를 확정한다. PvP 두 클라이언트는 같은 전투를 예측하고, 공개된 상대 입력이나 서버 확정 입력이 예측과 다를 때만 상태 링에서 되돌려 재시뮬한다. 전체 상태를 30Hz로 보내는 스냅샷 방식은 쓰지 않는다.
- PvP 입력은 상대가 **같은 틱의 자기 입력을 먼저 제출한 뒤**에만 중계한다(commit-before-reveal). 서버는 자기 시계로 틱을 확정하며, 살아 있는 입력 스트림의 누락에는 최대 6틱 조건부 대기 후 마지막 실제 마스크를 대체·감쇠한다. 늦은 입력은 지난 틱을 바꾸지 못한다.
- 용전(PvE)은 입력 지연 `D=0`으로 로컬에서 용까지 예측한다. 서버는 누락 입력을 최대 15틱 기다려 독립 시뮬 결과를 검증·확정한다. 관전자는 확정 입력만 적응형 6~15틱 버퍼 뒤에서 재생하며 롤백하지 않는다. 모든 봇 전투는 서버가 먼저 실행해 압축된 입력 리플레이를 보낸다.

### 9.2 전송·타이밍·제한
- Socket.IO WebSocket 전용 연결에서 입력·중계·확정의 빈번한 메시지는 **평면 JSON 정수 배열**로 전송한다(현재 바이너리 프레임 아님). 객체형 시작·제어·동기화 메시지는 스키마로 검증한다. 연결의 압축은 꺼져 있고, 재접속·갭 복구는 앱 수준 `fight:sync`를 쓴다.
- 서버의 공유 `setTimeout`/`setImmediate` 스케줄러가 전투 방마다 60Hz를 진행한다. 한 번에 최대 120스텝을 따라잡고 늦으면 `fight:retime`을 보낸다. 보드 `COMBAT` 동안 턴 타이머는 멈춘다. `fight:start`는 시드·설정·규칙 해시·빌드 버전·역할을 고정하고, `fight:go`는 서버 단조 시계의 틱 0을 알린다. 준비 제한은 6초, 시작 전 준비 구간은 90틱이다.
- PvP의 고정 입력 지연 `D`는 **각 클라이언트 자신의** 유효 RTT 구간에서 1~7틱을 고른다(PvE 0). 입력 시계는 서버 시각과 도착 여유를 기준으로 앞서 찍고, 서버가 확인한 여유로 ±3%(큰 오차는 ±5%) 시간 비율을 조절한다. 연결 품질이 나빠지면 예측 깊이와 대체 입력이 늘 수 있다. `simTick − confirmedTick` 상한은 PvP 40틱, PvE 120틱이고, 상태 링은 128칸·입력 링은 512칸이다.

### 9.3 메시지와 검증 (전체 이름은 [architecture.md §12](architecture.md))
| 메시지 | 방향 | 내용 |
|---|---|---|
| `fight:start` / `fight:ready` / `fight:go` | 서버→방 / 전투원→서버 / 서버→방 | 전투 설정·역할, 고정 `D`·RTT, 서버 시작 시각 |
| `fight:input` / `fight:relay` | 전투원→서버 / 서버→상대 | `fightId`, 틱, 최근 입력 마스크(최대 16개); 상대의 같은 틱 제출 뒤 중계 |
| `fight:confirm` | 서버→전투원·관전자 | 보통 2틱마다 확정된 양쪽 마스크·대체/봇/종료 플래그·품질·도착 여유; 30틱마다 상태 해시 |
| `fight:ping` / `fight:pong` / `fight:ack` | 클라이언트↔서버 | 시계·RTT 측정, 관전자 수신 확인과 백로그 관리 |
| `fight:control` / `fight:sync` / `fight:retime` | 서버→클라이언트 | 봇 인계, 전체 상태 복구, 서버 시계 재기준 |
| `fight:end` / `fight:replay` | 서버→방 | 서버 확정 결과·최종 해시 / 모든 봇 전투의 입력 리플레이 |

- 서버는 인증된 소켓에서 전투 좌석을 구하고, 입력의 형식·마스크·과거 틱·서버 현재 틱보다 30틱 넘는 미래 입력을 검사한다. 틱당 첫 입력이 유효하다. 입력·핑·제어 요청은 별도 속도 제한을 받는다. 클라이언트는 `hashCombatRules`, 전투 팩/넷코드 빌드 식별자가 다르면 해당 전투에 참가하지 않는다.

### 9.4 예측 표시·복구
- 클라이언트는 확정 입력과 해시를 상태 링에 반영하고 필요한 틱부터 재시뮬한다. 위치 보정은 렌더 복사본에만 적용하며, 48px를 넘거나 동작 범주가 달라지면 즉시 맞춘다. 이벤트는 ID/서명으로 재시뮬 중 재연결해 효과음 중복을 줄이고, KO와 결과는 확정 뒤 표시한다.
- 해시 불일치·확정 스트림 갭·재접속·백로그는 `fight:requestSync`/`fight:sync`로 복구한다. 관전자는 확정 입력을 재생하고 해시를 확인한다. 연결 단절 또는 입력 고갈 시 서버 봇이 이어받고, 복귀한 사람은 최소 3초 봇 유지와 미래 입력 3틱 확보 뒤 제어를 돌려받는다. 서버만 전투 결과를 `GameSession.submitCombatResult`에 넣는다.

### 9.5 현재 검증 범위와 측정
- `packages/netcode/test/netMatrix.test.ts`는 최대 500틱 고정 시드의 **가상 TCP** 두 클라이언트(`RollbackSession`)와 서버를 시험한다. 시작 전 입력을 보내고 지연·지터·손실·TCP 순서 막힘을 재현한다. 아래 수치는 두 클라이언트의 예측 깊이 p95(틱)이며 모든 조건에서 최종 해시·결과가 서버와 같고 거짓 디싱크는 0이었다.

| RTT / 지터 | 손실 0% | 손실 조건 |
|---|---:|---:|
| 20ms / ±5ms | 1 / 1 | — |
| 80ms / ±15ms | 6 / 5 | 0.5%: 10 / 11 |
| 150ms / ±20ms | 9 / 9 | 1%: 18 / 19 |
| 250ms / ±40ms | 15 / 15 | 2%: 33 / 33 |

- 손실 구간의 깊이는 [netcode-design-v2.md §8](research/netcode-design-v2.md)의 체감 목표를 충족하지 못한다. 이 시험은 전체 브라우저 `FightClient`의 적응 시계·렌더링이나 실제 플레이 체감을 검증하지 않는다. Socket.IO 통합 테스트는 서버 권위 용전, PvP commit-before-reveal, 관전자 수신을 확인한다. 브라우저 간 결정성·실제 회선 플레이테스트도 별도 검증이 필요하다.

## 10. 결정성·테스트
- 골든 리플레이 해시(Node + Playwright 3개 브라우저), 무작위 입력 1만 판 서버-클라이언트 해시 퍼즈, 고정 시드 전투 단위 테스트(프레임 데이터·피해 표·불의 고리·시간 종료 판정·불굴·회피 카운터).
- 직업 5종 × 대결 25쌍 + 용전의 스크립트 봇 대전 지표(평균 전투 시간, 시간 종료 비율, 승률)를 `pnpm sim`에 추가한다.
